# GH-867 startup observability inventory

Baseline: `8494a8e882e95c581f78d6baf059be56b998dcad` (clean `main`).

## Problem statement and owner constraints

`Manager.StartAll` seals composition and starts every admitted service sequentially before it binds the shared HTTP listener. The mandatory ComponentManager is itself a concurrent, fail-closed component-start barrier. One component whose `Start` remains in flight therefore keeps the shared HTTP surface, `/readyz`, and the separately managed metrics listener unbound. The observable result is connection refusal rather than an in-process account of admitted units, completed starts, current health, or the still-running start.

Issue #867 owner comments fix the boundary for this inventory: runtime service/component lifecycle state is ephemeral, process-local, new on every boot, and owned by ServiceManager/ComponentManager; `/readyz` reads direct in-memory manager observations; listener-bind diagnostics precede a component/service startup block; readiness combines admitted units having started with current health. NATS/KV/JetStream persistence or round trips, a readiness service, lifecycle framework/state machine, generalized supervisor, a new #867 OpenSpec, and a claim that `service-shutdown` governs component lifecycle are excluded. The issue's four-PR order is ComponentManager ownership, ServiceManager ownership, #1020 early process signal observation, then #867 startup observability. These are owner rulings, not new design claims.

## Current specifications, ADRs, and documentation

- **Direct specification collision:** `openspec/specs/framework-composition/spec.md:152-176` correctly requires the fail-closed component-start barrier but additionally says the process MUST NOT bring up HTTP or report service health while starts are outstanding/failed, and its failure scenario says HTTP is never brought up. The barrier portion aligns with #867; the HTTP-darkness clause conflicts with the issue owner's diagnostic-listener ruling. This is existing truth that must be reconciled without creating a new #867 OpenSpec, per owner ruling.
- `openspec/specs/framework-composition/spec.md:245-258,289-305` requires provider-first barriers without sleeps, polling, guessed readiness deadlines, dependency DAGs, or generalized scheduling, and says composition selection does not define Start/Stop mechanics. It blocks turning #867 into a startup scheduler.
- `openspec/specs/service-composition/spec.md:3-5` explicitly does not govern health/readiness. It requires seal before service Start, route binding, or OpenAPI exposure at `:106-125`, while its runtime-view requirement says readiness remains unchanged at `:244-264`. Moving bind timing is therefore a collision with existing route-exposure wording, not permission to invent a new composition capability.
- `openspec/specs/service-shutdown/spec.md:3-14` is narrowly service Stop and explicitly says component lifecycle belongs elsewhere. It contains accepted ComponentManager borrow-fence/failed-Start provisions at `:94-127`, but it is not valid authority for a claim that service shutdown governs components or startup readiness.
- `openspec/specs/runtime-context-ownership/spec.md:6-59` requires caller contexts, no retained Context, private cancellation/join authority only, and nil-before-action. The touched runtime owners currently satisfy that storage boundary.
- Accepted ADR-094 fixes one boot generation and process-local composition at `docs/adr/094-boot-only-composition-and-observable-rule-activation.md:35-56`, and requires signal-driven ordered shutdown without canceling runtime Start authority early at `:93-140`. Accepted ADR-095 distinguishes one-shot running Stop from retained failed-Start cleanup and rejects a lifecycle framework/catalog at `docs/adr/095-one-shot-running-lifecycle-with-retained-failed-start-cleanup-authority.md:24-59`.
- Historical ADR-058 deliberately keeps pprof early for wedged-boot diagnosis and rejects a boot engine, lifecycle-phase state machine, generalized subsystem abstraction, new registry/config schema, and big-bang migration at `docs/adr/058-boot-lifecycle-phases.md:390-424`.
- ADR-030 and `docs/operations/09-http-middleware.md:3-50` make the shared Manager mux the product middleware seam and require middleware registration before `StartAll`; `/readyz` is explicitly included. `service/doc.go:112-143` documents the current two-phase late-listen behavior and exact readiness meaning, so it will require consistency work if behavior changes.
- `service/doc.go:116-123` is internally stale as well: it says the HTTP server is created early and lists `/metrics` among shared-mux system endpoints. Production only creates the mux/system routes early; the shared listener is late as measured above, while `/metrics` belongs to the separate Metrics service/listener at `service/metrics.go:117-191` and `metric/handler.go:53-148`. This is a documentation collision across both listeners, not evidence that metrics is already available during startup.
- Active OpenSpec changes at baseline are unrelated (`agentic-loop-evidence-integrity-condition`, `align-standard-lifecycle-tests`, `close-graph-index-partial-start-subscriptions`, `cover-product-lesson-write-e2e`, `own-lesson-curator-contract`); none owns #867. Owner ruling is no new OpenSpec for this issue.

## Adopter seam inventory

Specific adopter 1: a product composition developer using `service.Manager` without reading its internals.

1. **What must they know today?** `StartAll` seals and blocks until all child Starts return; shared HTTP and a later metrics service do not bind until then; product HTTP middleware must be installed before StartAll. The optional dedicated listener has a separate API and omits `/readyz`. Component admission also includes non-lifecycle Discoverables, so admitted count is not interchangeable with lifecycle Start-participant or completed-Start count.
2. **What happens if they do nothing?** Their process can remain alive but externally dark during a slow component Start. No current API reports which admitted unit is in flight. Existing products compile because this is timing/observation behavior, not a signature mismatch.
3. **Where do they find out?** StartAll's public shape does not expose the timing. The two-phase behavior is in `service/doc.go:112-143`, middleware timing in `docs/operations/09-http-middleware.md:42-50`, and practical failure is connection refusal. Current discovery is therefore documentation and operations evidence, not typed feedback.
4. **What SHOULD they have to know?** Ideally nothing beyond existing composition and middleware setup. The framework managers already observe the admitted set, which members participate in lifecycle, exact Start invocations/results, and current Health calls; asking a product to publish or collapse those counts would duplicate authority.
5. **Observation vs prediction:** a product cannot correctly predict start duration, the blocked unit, or admitted count. The manager can observe actual admission and method completion directly.

Specific adopter 2: an operator/orchestrator polling `/readyz` and Prometheus.

1. **What must they know today?** Connection refusal means the shared listener has not bound; after binding, 200 `READY` means all current service self-statuses are running and `IsHealthy`, while 503 `NOT READY` means at least one is not. Metrics connection refusal may be caused by an earlier service block, not the Metrics service itself.
2. **What happens if they do nothing?** Docker healthchecks and scripts that wait specifically for HTTP 200 continue waiting through both refusal and 503. A consumer that equates TCP reachability with readiness would observe a timing change when diagnostics bind earlier. Consumers that parse the exact readiness text may also be sensitive to body changes.
3. **Where do they find out?** The current strings are documented externally by semstreams-ui and exercised in local tests; operator behavior is otherwise implicit in healthchecks/task scripts.
4. **What SHOULD they have to know?** Readiness status and current diagnostic facts, not manager internals, NATS subjects, bucket names, freshness epochs, or a startup timeout.
5. **Observation vs prediction:** the server can return the manager's current in-memory observation. No remote storage read or operator-supplied timing threshold is needed to reconstruct a fact the process already owns.

Specific adopter 3: an external component author implementing `LifecycleComponent`.

1. **What must they know today?** Start owns continuing work and must honor its context; Stop is caller-bounded; Health must report current component condition. They do not control Manager listener timing.
2. **What happens if they do nothing?** A legitimately slow Start remains a boot barrier and currently makes diagnostics dark; the owner's #867 boundary changes observation, not the component contract.
3. **Where do they find out?** `component/lifecycle.go:43-57` and component health interfaces; there is no readiness callback or publication requirement.
4. **What SHOULD they have to know?** No manager readiness math, lifecycle state subject, bucket, boot identity, or admitted-count protocol.
5. **Observation vs prediction:** ComponentManager sees when it invokes Start and when Start returns; the component author should not duplicate that observation.

## Exact remaining local gap

At baseline, manager control ownership and #1020's early signal observation are present, but startup observability is not. The missing facts are process-local manager observations of the current boot invocation that keep admitted components, lifecycle participants, and completed Starts distinct and can be read while `StartAll` is still blocked; the shared diagnostic HTTP and metrics listeners are not bound in that interval; current `/readyz` reads child self-status/health only and does not include ComponentManager admitted/participant progress; current counts exist only through later HTTP, heartbeat, saved-flow, and exported projection paths. Existing tests and two current spec clauses instead preserve HTTP darkness. This inventory makes no ruling on the eventual Go type, response body, metric names, internal split of route registration from listener bind, or migration spelling.
