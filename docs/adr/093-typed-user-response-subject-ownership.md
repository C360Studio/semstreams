# ADR-093: Typed User-Response Subject Ownership

## Status

**Accepted (2026-08-13); governance correction accepted (2026-08-14).** Breaking pre-v1 cross-repository contract
for SemStreams, SemDev, and SemTeams.

## Context

`user.response.>` named incompatible production meanings: registered `BaseMessage<agentic.UserResponse>`, flat rule
publish envelopes, and a flat governance error object. A SemDev durable consumed the broad family as a park-post work
queue but decoded only the flat rule shape, so a valid typed response was classified as malformed and acknowledged.

This was not a decoder-tolerance problem. The same prefix conflated a channel-addressed response, a product-owned
request for an external side effect, and orphan notifications with no reader. A union decoder or bridge would make
each adopter know every product contract and would hide the next incompatible writer.

## Decision

Reserve `user.response.>` exclusively for registered `agentic.user_response.v1` BaseMessages. The rule engine rejects
all three arbitrary subject-bearing actions—`publish`, `publish_agent`, and `approve`—both from their declared
subject and after runtime substitution when they target that family.

The dispatch default and all eight explicit shipped declarations name interface `agentic.user_response/v1`; the
production-merge census requires nine effective typed declarations.

SemDev park-post work moves to exact JetStream subject `semdev.park-post.request`, with port interface
`semdev.park_post_request/v1`. It remains a raw product contract generated by the rule publish action, not a
SemStreams payload-registry type. Both SemDev USER catalogs and both exact producer/consumer ports name the contract;
the conversation-channel durable owns the external post. The raw reader requires a canonical non-empty `entity_id`,
envelope `subject` exactly `semdev.park-post.request`, an RFC3339 `timestamp`, and `source` exactly `rule_engine`;
`properties` and `related_id` are optional.

Governance's unconsumed user-notification writer, `user_errors` port, and `notify_user` configuration are removed
without a replacement subject or typed response. Any raw `notify_user` presence, including `null`, fails as a
breaking migration error. Governance audit storage, metrics, logging, admin alerts, and violation events remain.
The audit store uses canonical valid KV key `violation.<id>` and the shared KV literal-key validator before bucket
lookup or NATS I/O. The rejected `violation:<id>` spelling gets no reader or conversion path because NATS KV never
accepted it and therefore no legacy audit record exists.

SemTeams retains typed response producers and its typed message-logger observer, but deletes exactly its two
unconsumed flat coordinator publish actions. Message-logger decoding is observability evidence, not a claim of
end-user delivery.

Adoption uses a fresh-state cut. There is no union decoder, bridge, alias, dual format, dual subscription, forwarding
subject, state conversion, or mixed-version compatibility lane.

## Consequences

Each surviving subject has one operation and one named payload contract. An adopter implements only its owned lane;
it does not inspect bytes to infer which product sent them. Unmigrated rule definitions and governance configuration
fail visibly instead of losing messages through tolerant decoding.

SemDev and SemStreams must land in breaking lockstep, with SemStreams agentic E2E and SemDev park-post E2E green
before landing. SemTeams cannot adopt the breaking SemStreams version until its flat-action removal and typed-decode
contract tests are green.

The reservation does not create a typed response delivery adapter or receipt contract. Message-logger remains an
observer. SemDev's existing bounded redelivery and graph-only definitive outcomes remain, and governance no longer
attempts an unconsumed user-facing publish.
